### 3-3 번에 대해 — 꼭 읽어 주세요

**회원이 서버에 요청 한 번으로 자기 지갑 잔고를 아무 숫자나 써넣을 수 있는 상태입니다.**

지갑 줄을 고칠 때 서버가 **"누구 줄인지" 는 확인하는데 "무엇으로 바꾸는지" 는
확인하지 않고** 있었습니다. 같은 파일의 다른 규칙 6곳에는 그 확인이 있는데
지갑 줄에만 빠져 있었습니다.

**⚠ 다만 이 파일로도 잔고 조작이 전부 막히지는 않습니다. 솔직하게 말씀드립니다.**

지금은 **거래 계산을 회원의 브라우저가 하고, 그 결과를 브라우저가 서버에 씁니다.**
그래서 **정상적인 거래와 손으로 고친 값이 똑같은 길로 들어옵니다.**
서버가 둘을 가려낼 방법이 없습니다. 잔고 쓰기를 막으면 **정상 거래도 저장이 안 됩니다.**

그래서 이 파일은 **확실히 회원 것이 아닌 칸만** 잠급니다.

```
잠급니다   기준자본 · 무상충전 누계 · 오늘 충전 횟수 · 사이클 번호 · 남의 줄로 옮기기
열어둡니다 지갑 잔액 · 누적 손익      ← 막으면 거래가 저장이 안 됩니다
```

**잔고 자체를 어떻게 할지는 대표님이 정하실 일입니다.** 세 가지 길이 있고
파일 맨 아래 `[4]` 에 정리해 두었습니다. 요약하면 —

```
(가) 거래 계산을 서버로 옮긴다        가장 확실. 대신 큰 공사
(나) 서버가 지갑을 다시 계산해 대조한다  손익 계산 규칙을 새로 정하는 일
(다) 지금처럼 두고 이상한 값을 찾아낸다  베타이고 회원이 소수라 이것도 합리적
```

**팀이 임의로 고르지 않았습니다. 정해 주시면 그대로 만들겠습니다.**

> **먼저 위 '읽기만 하는 파일' 3번(= 이 파일의 `[0]` 부분)을 돌려 주세요.**
> 저장소 파일과 서버가 다를 수 있어서, 서버에 직접 물어야 확정됩니다.
> `[0]` 은 표만 보여주고 아무것도 안 바꿉니다.

### 3-4 번에 대해 — 가입하는 순간의 구멍

**지금은 가입할 때 브라우저가 지갑 줄을 직접 만듭니다.**
서버는 **"본인 것이 맞나" 만 보고 "무슨 값을 넣는지는 안 봅니다."**

계급 점수는 이렇게 셉니다.

```
계급 자산 = 지갑 + 묶인 증거금 − 무상충전 누계(recharge_total)
```

무상충전 누계는 **빼는 칸**입니다. 그래서 가입할 때 여기에 **마이너스**를 실어 보내면
자산이 그만큼 **늘어납니다.**

```
recharge_total 에 -1,000,000 을 실어 가입하면
  계급 자산   100,000  →  1,100,000
  계급 점수   0점      →  약 3,459점
```

**거래를 한 번도 안 하고 계급이 올라갑니다.**

**3-4 를 돌리면 가입할 때 이 칸들이 전부 기본값으로 고정됩니다.**
무상충전 누계 · 오늘 충전 횟수 · 마지막 충전 시각 · 사이클 번호 네 개입니다.

> ### ⚠ 순서 — **3-3 을 먼저, 그다음 3-4**
>
> **3-4 하나만으로는 절반입니다.**
> 가입하는 순간은 3-4 가 막고, **그 뒤에 저장할 때는 3-3 이 막습니다.**
> 한쪽만 걸면 다른 쪽 길로 그대로 들어옵니다.
>
> ```
> 3-3 을 먼저 → 3-4
> ```
>
> 순서가 바뀌어도 **깨지지는 않습니다.** 다만 3-3 을 돌리기 전까지는
> 반쪽만 막힌 상태입니다.

- **정상 가입은 하나도 안 막힙니다.** 지금도 브라우저는 이 네 칸을 안 보냅니다
- **회원 데이터를 한 줄도 안 바꿉니다.** 앞으로 들어올 것만 막습니다
- **새 자물쇠를 달지 않습니다.** 이미 걸려 있던 것 하나의 내용만 늘립니다
- 몇 번을 눌러도 결과가 같습니다

**이미 들어온 게 있는지 먼저 보고 싶으시면 위 읽기 전용 `6번`을 돌려 주세요.**
`[1]` 표의 숫자가 **전부 0 이면 아무 일도 없었던 것**입니다.

> **아직 안 막는 것도 솔직하게 적어 둡니다** — 파일 안 `[4]` 절에 있습니다.
> 누적 손익(realized_pnl) · 사이클 시작 시각 · 지갑 잔액 자체는 이번에 안 건드렸습니다.
> **저희가 임의로 고르지 않았습니다.** 하라고 하시면 그때 하겠습니다.

### 왜 시드 충전권이 포지션 중에 막혀야 하나

무료 충전(하루 2번)과 재충전 이용권에는 **"포지션 들고 있으면 안 됨"** 이 이미
걸려 있습니다. **시드 충전권에만 빠져 있었습니다.**

청산 직전까지 몰린 상태에서 지갑을 채우면 청산 계산이 흔들려서,
그 회원만 유리해집니다. 같은 규칙으로 맞췄습니다.

## 3. 열 필요 없는 파일 — 눌러도 아무 일 없습니다

실수로 Run 하셔도 안전하도록 **미리 막아 두었습니다.**

| 파일 | 왜 막았나 |
|---|---|
| `supabase/cleanup-test-data.sql` | 회원 **전원 삭제** 파일. 지우는 부분을 막아 뒀습니다 |
| `supabase/schema-tl-monthly.sql` | TL 을 **한 달에 한 번** 주던 옛 방식. 실시간으로 바뀌었습니다 |
| `supabase/schema-tl-hotdeal.sql` | 상점은 살아 있고, **옛 TL 계산 부분만** 막았습니다 |
| `supabase/schema-tl-balance-fix.sql` | TL 잔액 표시 부분을 막았습니다. 지금은 3번 파일이 그 일을 합니다 |
| `supabase/schema-rank-assets.sql` | **계급을 매기던 옛 방식.** 지금은 1번 파일이 그 일을 합니다 |
| `supabase/schema-rank-badges.sql` | **계급 점수를 TL 로 매기던 더 옛 방식.** 계급장은 그대로 보입니다 |

이 파일들은 **기록으로 남겨 둔 것**입니다. 지우지 않았습니다.

> **계급 관련 두 파일을 왜 막았나**
> 1번 파일(`schema-rank-1000.sql`)을 돌린 뒤에 저 두 파일을 실수로 누르면,
> 회원 계급이 전부 **옛 기준으로 조용히 되돌아갑니다.**
> 오류도 안 나고 화면도 멀쩡해서 아무도 눈치채지 못합니다.
> 그래서 미리 막아 뒀습니다. 이제 눌러도 계급은 안 바뀝니다.
