## 한눈에

> **한 글자로 답하시면 되는 것 — 1 · 4 번 (A/B/C) · 6 · 7 · 8 번 (예/아니오)**
> **대표님이 직접 하셔야 하는 것 — 2 · 3 번 (SQL 실행) · 5 번 (폰 캡처)**
> **급하지 않은 것 — 6 · 7 번. 오늘 답 안 하셔도 아무도 안 막힙니다**

> **급한 순서로 하시면 — 2번 → 3번 → 8번 → 5번(캡처) → 4번 → 1번**

## 🔴 1. 대표 계정 잔고·실현손익을 어떻게 할지

### 무슨 일이 있었나

대표 캡처(2026-08-27 16:16 체결)에서 읽은 값 —

```
실현손익      -599,999,990원   ≈ -400,000 USDT
개시증거금     285,714,285원    ≈ 190,476 USDT
포지션        비트코인 241.652054 개 · 100배
```

### 감사팀이 확정한 것

**계산식은 정상입니다. 금액의 크기만 이상합니다.**

```
개시증거금 190,476.19 × 1.05 = 199,999.9995 ≈ 200,000.00
  → 진입 순간 지갑 잔고가 정확히 200,000 USDT 였습니다
  (js/trading.js:106-109 getMaxAffordableMargin 과 같은 식)

강제청산 1회의 실현손익 = -(margin + entryFee) = 그때 지갑에 있던 돈 전액
  지갑 100,000 → 정확히 -100,000
  지갑 200,000 → 정확히 -200,000
  → -400,000 = 100,000 전소 4회, 또는 200,000 전소 2회
```

**딱 떨어지는 200,000 은 "번 돈" 이 아니라 "받은 돈" 의 모양입니다.**
거래로 번 돈이면 187,342.11 같은 지저분한 숫자가 나옵니다.

### 선택지

| | 무엇 | 누가 하나 |
|---|---|---|
| **A** | 그냥 둔다 — 베타 테스트 흔적. 정식 오픈 때 한 번에 정리 | 아무것도 안 함 |
| **B** | 지갑 초기화 (100,000 으로 맞춤) | 대표가 포지션을 닫고 버튼을 누름 |
| **C** | 실현손익·거래기록까지 정리 | 본부장이 SQL 파일을 만들고 대표가 실행 |

**본부장 의견 — A 를 권합니다.** 베타이고 회원이 소수이며 정식 오픈 때 어차피 한 번 정리합니다.
**다만 랭킹에 대표님 값이 지금 보이고 있다면 B 나 C 가 낫습니다.**

⚠️ **랭킹에는 지금 안 보입니다** — `supabase/schema-leaderboard-floor.sql` 의 바닥 규칙 때문입니다.
**마이페이지에만 -400% 로 뜹니다.**

⚠️ **본부장 정정 (조사팀 지적)** — 처음에 "순손실이면 항상 0원" 이라고 적었는데 **틀렸습니다.**

```
바닥 규칙   랭킹수익금 = 전체합계 − min(0, 누적 최저점)

[-100, +30]  순손실인데 랭킹수익금은 +30    ← 0 이 아닙니다
```

**정확히는 "마지막 거래가 여태 최저점일 때만 0" 입니다.**
대표 계정이 지금 그 상태라 0으로 나오는 것이고, **손실 뒤에 조금이라도 벌면 그만큼 올라옵니다.**

**이 구분이 중요한 이유** — "순손실이면 항상 0" 으로 알고 있으면
**진짜 고장(바닥 뒤에 벌었는데 0으로 나오는 것)을 정상으로 넘기게 됩니다.**

**"A" 한 글자면 됩니다.**

```

→ 300 TL 짜리 한 장 = 자산 2배 = 정확히 +1000점 (상병)
```

**2026-08-24 대표 결정("계급을 사는 셈이라 충전받은 돈은 뺀다")이 TL 마켓 경로에만
적용되지 않은 것입니다.** `js/rank.js:154-163` 에는 반영돼 있습니다.

### (3) 실현손익이 최근 200건으로 잘려 서버를 덮어씁니다

**거래 200건이 넘는 회원은 화면의 실현손익이 평생 합계가 아니라 최근 200건 합계입니다.**

⚠️ **셋 다 가상 자산 회계라 본부장 재량 밖입니다.**

## 🔴 4. TL 마켓에서 팔리는 유일한 상품이 아무 효과가 없습니다

**조사팀이 찾고 본부장이 확인했습니다.**

```
레버리지 x100배 이용권   50 TL   지금 TL 마켓에서 유일하게 살 수 있는 상품입니다

js/leverage-gate.js:35             var DEFAULT_MAX = 100;   ← 이용권 없이도 이미 100배
supabase/schema-tl-market.sql:377  effect_value = 100

currentMax() = Math.max(100, 100) = 100
```

**회원이 50 TL 을 내고 사면 아무것도 안 달라집니다.**

### 왜 이렇게 됐나

이용권을 만들 때는 **기본 50배 + 이용권 쓰면 100배** 구조였습니다.
`js/leverage-gate.js:31` 주석에 그렇게 적혀 있습니다 —

> 지금은 모든 사용자에게 100배를 열어둡니다(이용권 없이도 100배 가능).
> 나중에 이용자가 많아지면 이 값을 50으로 내리기만 하면 즉시 전환됩니다.

**오늘 "일단 100배로 냅두자" 결정으로 이용권이 무의미해졌습니다.**
누구 잘못이 아니라 결정의 결과입니다.

### 선택지

| | 무엇 | 무엇이 바뀌나 |
|---|---|---|
| **A** | 이 상품을 판매 중지 | 회원이 헛돈 쓰는 것만 막습니다. 가장 간단합니다 |
| **B** | 기본 상한을 50배로 내린다 | 이용권이 다시 의미를 갖습니다. **회원 전원의 레버리지가 반으로 줄어듭니다** |
| **C** | 이용권 효과를 125배로 올린다 | 엔진 상한이 125라 실제로 열립니다. **오늘 "100배" 결정과 봉인 테스트에 걸립니다** |

**본부장 의견 — A 를 권합니다.** B 는 오늘 결정을 뒤집는 것이고,
C 는 `js/trading.js:96` 엔진 상한까지 밀어붙이는 것이라 대표 결재 없이는 못 합니다.

⚠️ **이미 산 회원이 있으면 환불 여부도 정하셔야 합니다.**
**`supabase/조회-잔고출처-2026-08-27.sql` 3번 블록**이 누가 무엇을 샀는지 보여줍니다.

⚠️ **효과 없는 상품이 세 개 더 있습니다** — 포지션 훔쳐보기 · 수수료 할인권 · 포지션 보호권.
**TL 만 빠지고 아무 일도 안 일어납니다.** 셋 다 지금 판매 중지로 보이지만 서버 확인이 필요합니다.

## 🟠 5. 로그인한 폰 화면 캡처

**본부장과 팀은 로그인하지 않습니다.** 비밀번호를 입력하지 않는 것이 원칙입니다.
그래서 **로그인해야 보이는 네 곳을 아무도 못 봤습니다.**

```
포지션 표 실제 행   미체결 주문   내 자산 패널   마이페이지 회원 화면
```

### 필요한 캡처

| 무엇 | 폭 | 왜 |
|---|---|---|
| 포지션 표 | 폰(360) | 더보기 버튼 · 18칸 펼침 · 밀기 힌트 · 강제청산가가 읽히는지 |
| 포지션 표 | 노트북(1440) | 같은 것을 넓은 화면에서 |
| 주문 패널 잠금 안내 | 폰(360) | 오늘 새로 만든 덮개. 글자가 잘리는지 |
| 지갑 초기화 경고 창 | 아무 폭 | 잔고 10만 초과 상태에서 눌러 경고가 뜨는지 (창 뜨면 취소 눌러도 됩니다) |

**이 넷을 주시면 오늘 팀들이 달고 있는 "확인 못 한 것" 이 거의 다 닫힙니다.**

## 🔴 8. 가입할 때 랭킹 점수를 만들어낼 수 있습니다

**2026-08-28 새벽에 수리팀이 찾았습니다. 조사팀이 "이득 없음" 이라 했던 칸 하나가 실제로는 이득이 됩니다.**

### 무슨 일인가

**가입할 때 지갑 줄을 만드는 것은 서버가 아니라 회원의 브라우저입니다.**

```
js/auth.js:317        가입하면 브라우저가 직접 지갑 줄을 만듭니다
supabase/schema.sql:50 서버는 "본인 것이 맞나" 만 봅니다
                       무슨 값을 넣는지는 안 봅니다
```

시작 잔고는 `force_starting_balance()` 가 100,000 으로 덮어써서 안전합니다.
**그런데 그 함수가 덮는 것은 잔고와 기준자본 두 칸뿐입니다.**

### 계급 점수가 이렇게 계산됩니다

```
supabase/schema-rank-1000.sql:255-268
  계급 자산 = 지갑 + 포지션증거금 + 미체결증거금 − recharge_total
                                                    ↑ 충전한 만큼 빼는 칸
```

**충전한 적이 없으면 0이어야 하는 칸인데, 가입할 때 원하는 값을 넣을 수 있습니다.**

```
recharge_total 에 -1,000,000 을 실어 가입하면
  계급 자산   100,000  →  1,100,000
  계급 점수         0  →  약 3,459점
```

### 얼마나 급한가

```
지금 회원  대표님 친구분들 소수 (베타)
실제 피해  아직 없습니다. 누가 했는지는 서버를 봐야 압니다
난이도     브라우저 개발자 도구를 열 줄 알면 됩니다
```

**돈이 나가지는 않습니다. 랭킹 순위만 바뀝니다.**
**다만 정식 오픈하면 랭킹이 회원에게 실제 가치가 생깁니다.**

### 막는 방법은 정해져 있습니다

**새 트리거를 안 답니다.** 이미 걸려 있는 `force_starting_balance()` 본문에
칸 몇 개를 더 덮게 하면 끝납니다.

```
지금 덮는 것   initial_balance · balance
더 덮을 것     recharge_total · recharge_count · last_recharge_at · cycle_no
```

⚠️ **잠금함수를 INSERT 에 다는 방식은 안 됩니다.** PostgreSQL 이 거부합니다
(`OLD` 가 INSERT 에는 없어서 SQLSTATE 55000). 그건 이미 확인했습니다.

### 대표님이 정하실 것

> **지금 막을까요?**
>
> **예** → SQL 파일을 만들어 드립니다. 대표님이 Run 하시면 됩니다. 회원 영향 0
> **아니오** → 정식 오픈 전까지 미룹니다

**"예" 를 권합니다.** 회원에게 아무 변화가 없고, SQL 한 번이면 끝납니다.

⚠️ **이미 누가 넣었는지는 서버를 봐야 압니다.** 2번 SQL 을 돌리시면 같이 나옵니다.
