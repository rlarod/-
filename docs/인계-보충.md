# 인계 문서 보충 — 환경 변경 안내 (2026-08-21)

기존 인계 문서(`TL 프로젝트 — Claude Code 인계 문서`)와 **함께** 읽는다.
기존 문서의 내용은 대부분 유효하나, **실행 환경이 바뀌어 7번 항목이 무효**가 되었다.

# 2. ⭐ 가장 중요한 변화 — 차단이 풀렸다

기존 문서 7번의 이 내용은 **더 이상 해당되지 않는다.**

> ~~이 환경에서 Supabase·바이낸스가 차단돼 있습니다. 시세도 채팅도 안 들어옵니다.~~
> ~~그래서 가짜 서버를 끼워 넣고 테스트하는 패턴을 많이 씁니다.~~

**이제는 진짜로 검증할 수 있다.**

- 실제 바이낸스 시세가 들어온다 → 시세 변동에 따른 손익 갱신을 진짜로 볼 수 있다
- 실제 Supabase에 붙는다 → 랭킹·거래내역·TL이 서버에 제대로 저장되는지 확인 가능
- 실제 강제청산이 발생하는 것을 관찰할 수 있다

## 그래서 검증 기준이 올라간다

이전에는 "가짜 서버로 통과"가 최선이었다. **이제는 그걸로 부족하다.**

- ❌ "테스트 통과했습니다" → 불충분
- ❌ "코드상 정상입니다" → 불충분
- ✅ **"실제로 눌러봤고, 실제 시세로 손익이 갱신됐고, 캡처가 이것입니다"** → 이게 기준

기존 자동 테스트(42개 파일 / 1,571개)는 계속 유효하다. 다만 **자동 테스트 통과 = 정상이 아니다.**
가짜 서버 기준으로 짜인 테스트라, 실제 환경에서만 드러나는 문제는 못 잡는다.

## ⚠️ 실서버에 붙는다는 것의 위험

실제 Supabase에 연결된다는 것은 **친구들의 진짜 데이터를 건드릴 수 있다**는 뜻이다.

- 테스트한다고 회원 데이터를 지우거나 초기화하지 않는다
- 랭킹·거래내역에 테스트 흔적을 남기지 않는다. 남겼으면 보고한다
- SQL은 여전히 대표가 직접 실행한다. 마음대로 돌리지 않는다
- `WHERE` 없는 DELETE·UPDATE는 절대 시도하지 않는다

# 3. 무효가 된 기술 정보

## Playwright 경로
```
❌ /opt/pw-browsers/chromium-1194/chrome-linux/chrome
```
Windows에는 이 경로가 없다. **브라우저 검증은 `agent-browser` 스킬로 한다.**

## md5sum (수정 금지 파일 확인)
Windows PowerShell에는 `md5sum`이 없다. 대신:

```powershell
Get-FileHash -Algorithm MD5 js\trading.js, js\ui.js, js\auth.js, `
  js\supabase-sync.js, js\chat.js, js\leaderboard.js, js\admin.js, `
  js\season.js, js\board.js, js\orderbook.js, js\chart.js, js\websocket.js
```

Git Bash에서는 기존 `md5sum` 명령이 그대로 동작한다.
**둘 중 편한 쪽을 쓰되, 매 작업 전후로 반드시 확인한다.**

## 로컬 서버
기존 문서: `python3 -m http.server 8899`
현재 `package.json`: `npm run dev` → `serve -l 3000`

**둘 다 된다.** `npm run dev` 쪽을 기본으로 쓰고, 주소는 `http://localhost:3000`.
Python이 편하면 8899도 무방하나 **팀 전체가 같은 주소를 써야 혼선이 없다.**

# 4. 조직 구조와의 연결

새로 만든 조직(`조직도.md`, `점검팀.md`)에 기존 문서의 규칙을 그대로 얹는다.

## 수정 금지 파일 12개 — 모든 팀 최우선 규칙 ⭐

```
js/trading.js       js/ui.js          js/auth.js        js/supabase-sync.js
js/chat.js          js/leaderboard.js js/admin.js       js/season.js
js/board.js         js/orderbook.js   js/chart.js       js/websocket.js
```

- **수리팀·개발팀·디자인팀 모두 한 글자도 고치지 않는다**
- 필요하면 별도 모듈로 우회한다 (기존 문서 1-1의 패턴 참고)
- **본부장은 게이트 2에서 이 12개 파일의 해시를 반드시 확인한다.**
  하나라도 바뀌었으면 무조건 반려한다. 예외 없다

## 기존 문서의 원칙이 조직 규칙보다 우선한다

| 기존 문서 | 적용 |
|---|---|
| 1-1 수정 금지 파일 | 모든 팀. 위반 시 즉시 반려 |
| 1-2 기능·데이터 삭제 금지 (CSS로 숨기고 마크업 보존) | 디자인팀·개발팀 |
| 1-3 가짜 데이터·숫자 금지 | 모든 팀 |
| 1-4 막히면 추측 말고 중단·보고 | 모든 팀 |
| 4번 디자인 팔레트 (개미톡 픽셀 추출값) | **디자인팀은 이 색을 임의로 바꾸지 않는다** |

> ⚠️ 내가 앞서 드린 디자인 지침("보라·파랑 그라데이션 금지" 등)보다
> **기존 문서 4번의 확정 팔레트가 우선**한다. 이미 픽셀로 뽑아 확정한 값이다.

## 손익·랭킹 계산은 여전히 대표 확인

베타 기간이라 가상 자산은 본부장 재량으로 풀었지만, **손익·랭킹 계산식은 예외**로 둔다.
기존 문서 3번에 "여기 손대기 전에 반드시 사용자에게 확인하세요"라고 명시돼 있고,
가장 오래 걸린 부분이며 여러 번 틀렸던 영역이다.

**계산식 변경은 대표 확인 후 진행한다.** 표시(display) 보정은 재량.

# 5. 점검팀 첫 임무 — 문서 검증

기존 문서 4번은 이렇게 주장한다:

```
자동 테스트   42개 파일 / 1,571개 통과 / 실패 0
수정 금지 파일  12개 전부 무변동
화면 점검     PC 1920 / 노트북 1440 / 모바일 390 — 오류 0건, 가로 스크롤 없음
메뉴 11개     전부 클릭 — 오류 0건
```

**이것부터 실제 환경에서 다시 확인한다.** 문서를 믿고 시작하지 않는다.

## 확인 순서

1. `npm test` 실행 → 정말 1,571개 통과 / 실패 0 인가
2. 수정 금지 파일 12개 해시 대조 → 기준값과 같은가
3. **가로 스크롤 재확인** ⭐ — 아래 별도 항목
4. 메뉴 11개 전부 클릭 → 오류 0건이 맞는가
5. `supabase/health-check.sql` 파일을 읽고, 대표에게 실행을 요청한다
   (SQL은 대표가 Supabase SQL Editor에서 직접 돌린다)

## ⭐ 최우선 확인 — 가로 스크롤 모순

**문서는 "가로 스크롤 없음"이라 하는데, 대표가 보낸 캡처에서는 오른쪽이 잘려 있었다.**

잘린 것으로 보인 요소:
- 오른쪽 사이드바 `보유 TL` 숫자
- `로그아웃` 버튼이 `로그`까지만 보임
- 실시간 채팅의 금액 끝자리 (`+332,940,951원 익절했습니다` 마지막 글자)
- 강제청산 알림 `(-55,007,76...원)`

**확인 방법**
1. 메인 화면을 1920 / 1440 / 390 으로 각각 연다
2. `document.body.scrollWidth` 와 `window.innerWidth` 를 비교한다
   (scrollWidth가 더 크면 가로 스크롤 발생)
3. 오른쪽 끝 요소가 전부 보이는지 캡처로 확인한다

**결과에 따라**
- 가로 스크롤 **있음** → P1로 즉시 처리. 그리고 **기존 점검이 왜 못 잡았는지**도 보고한다
- 가로 스크롤 **없음** → 대표의 캡처 도구가 일부만 찍은 것. "문서 내용 확인됨"으로 보고

**둘 중 하나로 반드시 결론을 낸다.** "아마 캡처 문제일 것"으로 넘기지 않는다.

## 그 외 확인 요청

- **호가창 단위 불일치** — 헤더 `가격(USDT)` vs 값 `110,791,200원`.
  원화 모드에서 헤더가 안 따라가는 것으로 보임
- **공개 저장소 보안** — 저장소가 Public이다. `service_role` 키나 비밀번호가
  코드에 있는지 확인한다. **찾기만 하고 고치지 않는다.** 발견 즉시 대표에게 보고

# 6. 본부장 백로그 (기존 문서 5번에서 이관)

기존 문서의 "남은 일"을 등급을 매겨 옮긴다. 순서는 본부장이 조정한다.

## 오픈 전 필수
| 항목 | 담당 | 비고 |
|---|---|---|
| 개인정보처리방침 페이지 | 개발팀 | 네이버 검수 필수 |
| 네이버 검수요청 | **대표** | 영업일 2~3일 |
| TL이 계좌 초기화 때 사라지는 문제 | 수리팀 | 72,560 → 60. 원인 미확정 |

## 미해결
| 항목 | 담당 | 비고 |
|---|---|---|
| 채팅창 위아래 흔들림 | 수리팀 | `?jitter=1` 진단 도구 있음. **측정부터 할 것** |
| 강제청산 알림 문구 | 디자인팀 | "(증거금 -55,007,767원)" 제안. 대표 답변 대기 |

## 대표가 보류시킨 것 — 건드리지 않는다
- 강제청산 수수료 (바이낸스는 명목가 1.25~2% 별도) → "아직 건들지마"
- 펀딩비 미납분 → 청산 로직(수정 금지) 관련이라 보류
- 주문창 본전 가격 표시 → "하지마"

## 논의만 하고 미적용
- **TL 경제 설계** — 현재 커피 한 잔(2,500 TL)에 190회 거래 필요.
  제안식 `1500 × log₂(1 + 수익/1천만)`.
  화면(`js/rank.js`)과 서버(`tl_earned`) 양쪽을 함께 고쳐야 함. **대표 확인 필요**
- 기존 비밀번호 회원을 카카오·네이버에 연결 → 필요 여부 미결정

# 7. 서버 함수 중복 문제 (기존 문서 6번 강조)

```
get_leaderboard   파일 4개
reset_season      파일 3개
rank_points_all   파일 3개
tl_balance_info   파일 2개
```

> **어느 파일을 마지막에 실행했느냐에 따라 서버 동작이 달라진다.**
> 파일만 봐서는 서버의 실제 상태를 알 수 없다.

**랭킹 관련 문제를 다룰 때는 반드시 `health-check.sql` 결과부터 확인한다.**
코드를 읽고 "이렇게 동작할 것"이라 단정하지 않는다.

SQL 실행은 대표가 한다. 팀은 **어느 파일을 실행해야 하는지 알려주기만** 한다.
