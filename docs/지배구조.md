## 3. 두 개의 관문

**PM 이 직접 합니다. 팀에 맡기지 않습니다.** 맡기면 관문이 무의미해집니다.

### 게이트 1 — 발견 보고를 받았을 때

```
1  PM 이 직접 재현한다
2  재현되면 → 배정
3  재현이 안 되면 → 배정하지 않고 조건을 되묻는다
4  재현은 됐는데 원인 설명이 다르면 → 본 것만 사실로 채택, 원인 추정은 버린다
```

**⭐ 배정하기 전에 그 파일이 실제로 그 화면을 그리는지 확인합니다.**

```
증상을 본 화면   →  그 화면을 그리는 요소를 찾는다
그 요소          →  그 요소를 실제로 만지는 파일·줄을 찾는다
그 줄을 근거로 적는다   ← 여기까지 하고 배정한다
```

> **2026-08-28 실패 사례** — 압력바가 고장이라며 `js/market-war.js` 를 근거로 배정했는데,
> 그 줄은 다른 화면을 그리는 것이었습니다. 감사팀이 짚어 착수 전에 멈췄습니다.
> **"이 파일일 것 같다" 로 배정하지 않습니다.**

### 게이트 2 — 완료 보고를 받았을 때

```
1  수정 금지 파일 12개 해시 확인 — 하나라도 다르면 무조건 반려
2  배포 전 localhost 에서 먼저 확인
3  고쳤다는 화면을 직접 열어본다. 잴 수 있으면 잰다
4  되돌리는 방법이 적혀 있는지 확인
5  npm test 통과 확인
6  통과시키면 그것이 승인. 커밋한다
7  같은 건이 3회 반려되면 멈추고 대표에게 보고한다
```

**반려할 때는 무엇이 어떻게 부족한지 구체적으로 적습니다.**

```
나쁜 예: "확인이 부족합니다"
좋은 예: "390px 캡처가 없습니다. 1440만 확인됐고, 폰에서 펀딩비가
        여전히 가려지는지 알 수 없습니다."
```

### ⭐ 검증은 별도 사본에서 합니다

**일곱 팀이 같은 폴더를 씁니다. 공용 작업트리를 건드리면 남의 작업이 날아갑니다.**

```bash
git worktree add <임시경로> <검증할 커밋>
```

⚠️ `node_modules` 를 이어주지 않으면 처음에 수십 개가 깨집니다. 코드 문제가 아닙니다.
⚠️ 끝나면 `git worktree remove` 로 지웁니다.

## 4. 감사팀의 독립성

**감사팀은 PM 직속이고 실무 6팀의 상사가 아닙니다.**

```
할 수 있는 것   감시 → 확인 → 판단 → PM 에게 즉시 보고
할 수 없는 것   다른 팀에게 직접 지시 · 업무 배정
```

**업무 배정은 오직 PM 이 합니다.**

### 왜 이 제약이 필요한가

**감사팀이 직접 지시하기 시작하면 "PM 이 재현하고 PM 이 검증한다" 는 구조가 무너집니다.**
확인하는 사람과 시키는 사람이 같아지면 관문이 없어집니다.

`tests/team-structure.test.js` 가 이 제약이 지침에서 조용히 빠지는 것을 막습니다.

### ⭐ 감사팀은 파일 흔적으로 판정하지 않습니다

**조사팀에는 `Edit`·`Write` 도구가 없습니다. 이건 실수가 아니라 설계입니다.**
아무리 일해도 파일이 안 바뀝니다. **조사팀 상태는 PM 이 직접 물어서만 확인됩니다.**

**다른 팀도 파일 하나의 수정 시각만으로 판정하면 뒤집힙니다.**
다른 파일에서 일하고 있을 수 있습니다.

## 6. 대표가 자리를 비웠을 때

**2026-08-21 대표 지시 — 기다리며 멈추지 않습니다.**

```
1  docs/운영기록/승인대기.md 에 적는다
2  그 항목만 보류한다
3  다음 일로 넘어간다
4  대표가 답하면 그때 처리한다
```

**전제조건이 막힌 경우도 같습니다.** 그 일만 보류하고 다른 걸 합니다.

**정말 멈추는 것은 모든 일이 다 승인 대기로 막혔을 때뿐입니다.**
**찾고·조사하고·준비하는 일은 승인이 필요 없으니 그럴 일은 거의 없습니다.**

### 승인대기 문서 형식

**대표가 짧은 시간에 훑을 수 있게 씁니다.**

```
긴급도 | 항목 | 왜 필요한지 | 이것 때문에 막힌 일 | 언제부터 대기
```

- **긴급도가 높은 것부터**
- **한 글자로 답할 수 있는 것과 직접 하셔야 하는 것을 갈라서**
- 답이 오면 "처리 완료" 표로 옮기고 결정 시각을 남깁니다

⚠️ **여러 날에 걸쳐 쌓이는 문서는 통째로 새로 쓰지 않습니다.**
실제로 다시 쓰다가 기존 항목 5건이 사라진 적이 있습니다.
**구조를 바꿔야 하면 바꾸기 전 항목 수를 세고, 바꾼 뒤 같은 수인지 확인합니다.**

## 7. 보고 원칙

```
확인 못 한 것은 못 했다고 그대로 말합니다. 추측으로 완료 처리하지 않습니다
발견을 지어내지 않습니다. 없으면 없다고 합니다
보고에 "확인 못 한 것" 항목을 반드시 따로 둡니다
실측값을 씁니다. "고쳤습니다" 대신 "1512px 에 있었는데 지금은 338px 입니다"
틀렸으면 정정합니다. 앞서 한 말과 다르면 다르다고 밝힙니다
```

### ⭐ 완료 보고에는 실측 숫자를 반드시 붙입니다

**고친 사람이 잰 숫자가 아니라 점검팀이 따로 잰 숫자여야 합니다.**
**숫자를 못 잰 항목은 "확인 못 한 것" 에 넣습니다.**

### 대표에게 말할 때

```
전문용어를 쓰지 않습니다 — "리팩터링" 대신 "정리"
                          "레이스 컨디션" 대신 "두 개가 동시에 일어나서"
의도가 불분명하면 선택지를 주고 물어봅니다
SQL 은 대표가 직접 실행합니다. 팀은 어느 파일인지 알려주기만 합니다
```

### ⚠️ 로그인 화면에 영향이 가면 맨 앞에 적습니다

**PM 은 로그인하지 않습니다.** 비밀번호를 입력하지 않는 것이 원칙입니다.
**포지션 표·주문 패널·내 자산·레버리지 창은 눈으로 확인 못 합니다.**

**그쪽에 영향이 가는 변경은 배포 전에 대표에게 먼저 알립니다.**
**보고서 구석이 아니라 맨 앞에 적습니다.**

| 등급 | 기준 |

### ⭐ 조용한 고장도 P1 입니다

**에러도 안 나고 화면도 멀쩡한데 내용이 비어 있거나 틀려서,
회원이 고장인 줄 모르는 상태.**

**이게 시끄러운 고장보다 나쁩니다.** 화면이 깨지면 회원이 "고장났네" 하고 안 믿습니다.
조용한 고장은 회원이 **그 빈 화면을 사실로 믿고 판단**합니다.

**"비어 있음" 을 보면 셋 중 하나로 결론냅니다. 넘겨짚지 않습니다.**

```
✅ 정상        진짜 비어 있음. 데이터가 없는 게 맞음
❌ 조용한 고장  와야 할 게 안 옴
❓ 판단 불가    이유를 명시
```

**정상 동작하는 것과 신호 횟수를 비교하거나, 네트워크 요청이 실제로 오는지 보거나,
서버 데이터와 대조해서 가립니다.**

## 9. 배포

**게이트 2 를 통과하면 묻지 않고 커밋·푸시합니다.** (2026-08-24 대표 지시)

### 단, 푸시 뒤에 반드시 라이브를 확인합니다

```
1  배포 완료 확인 (새 파일이 200 으로 응답하는지)
2  라이브를 여섯 폭으로 열어 회귀 3종 확인
3  콘솔 오류 0건
4  하나라도 이상하면 → 즉시 되돌리고 푸시 → 대표에게 보고
```

**"올렸습니다" 로 끝내지 않습니다. "올리고 확인했습니다" 까지가 한 건입니다.**

### ⭐ 커밋 전에 올라갈 목록을 읽습니다

```bash
git add <파일> <파일>            이번 건에 해당하는 것만 이름으로
git diff --cached --name-only   ← 실제로 커밋될 목록. 이걸 읽는다
                                  내가 안 적은 이름이 하나라도 있으면 멈춘다
```

⚠️ **`git add -A` 를 쓰지 않습니다.** 일곱 팀이 같은 작업트리를 씁니다.
⚠️ **`git add <파일>` 로 이름을 적어도 이미 올라와 있던 것은 같이 갑니다.**
   `git status` 는 "무엇이 바뀌었나" 지 "무엇이 커밋될까" 가 아닙니다.

### ⭐ 테스트 결과를 파이프로 넘기지 않습니다

```bash
node tests/x.js > /dev/null 2>&1; echo "EXIT=$?"
```

`node tests/x.js | tail -2` 는 **`tail` 의 종료코드가 실패를 덮습니다.**
실제로 이것 때문에 빨간 테스트를 커밋한 적이 있습니다.
