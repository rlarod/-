## [P1] 최근 체결 목록이 영구히 비어 있음

### 원인

**확인됨 (추측 아님).**

`js/config.js` 131~138행의 `buildCombinedStreamUrl()` 이 만드는 접속 주소가 이것입니다.

```
wss://fstream.binance.com/market/stream?streams=btcusdt@kline_1m/btcusdt@ticker/btcusdt@trade/btcusdt@markPrice@1s
```

바이낸스 선물은 2026-04-23 주소 개편에서 스트림을 경로별로 나눴는데,
**체결(`@trade`) 스트림은 `/public` 경로에만 있고 `/market` 경로에는 없습니다.**
그런데 바이낸스는 없는 스트림 이름을 받아도 **오류를 내지 않고 연결을 유지**합니다.
그래서 연결은 멀쩡하고, 같은 연결의 kline·ticker·markPrice 는 정상으로 오는데,
`@trade` 만 **한 건도 안 옵니다.**

`js/websocket.js` 125행의 `data.e === "trade"` 분기가 영원히 실행되지 않고,
131행의 `App.Bus.emit("trade:tick", ...)` 도 영원히 실행되지 않습니다.
`js/trades.js` 는 정상입니다 — 올 것이 안 올 뿐입니다.

**끊기는 지점은 2번입니다** (본부장이 제시한 4가지 중):
구독 URL 에 이름은 넣지만, 그 경로에 그 스트림이 없어서 메시지가 안 옵니다.

#### ① 새 파일 `js/trade-stream-fix.js` (신규)

호가창(`js/orderbook.js` 70행)이 이미 쓰고 있는 것과 **똑같은 방식**입니다 —
기존 연결을 건드리지 않고 자기 연결을 따로 엽니다.

```js
/* js/trade-stream-fix.js — App.TradeStreamFix
 * 체결(@trade)은 /public 경로에만 있는데 websocket.js 의 연결은 /market 이라
 * 한 건도 오지 않습니다. websocket.js(수정 금지)를 건드리지 않고,
 * 호가창과 같은 방식으로 체결 스트림만 따로 받아 'trade:tick' 을 대신 방송합니다.
 * 바이낸스 화면의 "최근 체결"과 같은 집계 체결(@aggTrade)을 씁니다.
 */
window.App = window.App || {};

App.TradeStreamFix = (function () {
  "use strict";

  var sock = null;
  var delay = 0;
  var synthetic = null; // 5s/15s 간격용 — websocket.js 148~163행과 같은 규칙

  function url() {
    return "wss://fstream.binance.com/market/ws/" +
      App.Config.getActiveSymbol().toLowerCase() + "@aggTrade";
  }

  function onTrade(d) {
    var price = parseFloat(d.p);
    if (isNaN(price)) return;
    var qty = parseFloat(d.q) || 0;

    App.Bus.emit("trade:tick", {
      symbol: d.s,
      price: price,
      qty: qty,
      isBuyerMaker: !!d.m,
      time: d.T || Date.now()
    });

    // 비-native 간격(5s/15s)일 때만 캔들·현재가를 대신 만들어 줍니다.
    // native 간격일 때는 websocket.js 의 kline 스트림이 이미 하고 있으므로
    // 절대 내보내지 않습니다(두 번 나가면 차트가 어긋납니다).
    var interval = App.Config.getActiveInterval();
    if (App.Config.isNativeInterval(interval)) return;

    var bucketSec = App.Config.intervalToSeconds(interval);
    var tSec = d.T ? Math.floor(d.T / 1000) : Math.floor(Date.now() / 1000);
    var bucket = Math.floor(tSec / bucketSec) * bucketSec;
    if (!synthetic || synthetic.time !== bucket) {
      synthetic = { time: bucket, open: price, high: price, low: price, close: price, volume: qty };
    } else {
      synthetic.high = Math.max(synthetic.high, price);
      synthetic.low = Math.min(synthetic.low, price);
      synthetic.close = price;
      synthetic.volume += qty;
    }
    App.Bus.emit("kline:update", { symbol: d.s, candle: synthetic });
    App.Bus.emit("price:update", { symbol: d.s, price: price, time: Date.now() });
  }

  function connect() {
    var s;
    try { s = new WebSocket(url()); } catch (e) { retry(); return; }
    sock = s;
    s.onopen = function () { delay = App.Config.RECONNECT_MIN_MS; };
    s.onmessage = function (evt) {
      var d;
      try { d = JSON.parse(evt.data); } catch (e) { return; }
      if (!d || d.e !== "aggTrade") return;
      onTrade(d);
    };
    s.onerror = function () { try { s.close(); } catch (e) {} };
    s.onclose = function () { retry(); };
  }

  function retry() {
    setTimeout(connect, delay || App.Config.RECONNECT_MIN_MS);
    delay = Math.min((delay || App.Config.RECONNECT_MIN_MS) * 1.6, App.Config.RECONNECT_MAX_MS);
  }

  function init() {
    connect();
    App.Bus.on("interval:change", function () { synthetic = null; });
  }

  return { init: init };
})();
```

#### 왜 `@aggTrade` 인가 (선택 근거)

| | `/public/ws/…@trade` | `/market/ws/…@aggTrade` ← 권장 |
|---|---|---|
| 실측 유량 | 초당 **92건** | 초당 **29건** |
| 내용 | 체결 1건씩 전부 | 같은 가격·같은 주문 체결을 묶음 |
| 바이낸스 화면 | 다름 | **바이낸스 "최근 체결"과 같은 것** |
| 필드 | `p q m T s` | `p q m T s` (동일) |

`market-war.js` 는 체결 1건마다 최근 80개 배열을 정렬합니다.
초당 92건이면 초당 92회 정렬이라 저사양 폰에서 부담이 됩니다.
바이낸스 화면과 맞추는 목적으로도 `@aggTrade` 가 맞습니다.
**체결 1건 단위가 꼭 필요하다고 판단되면** 주소만 `/public/ws/...@trade` 로 바꾸고
`d.e !== "aggTrade"` 를 `d.e !== "trade"` 로 바꾸면 됩니다 (둘 다 실측으로 동작 확인).

## [백로그] TL 이 계좌 초기화 때 사라지는 문제 (72,560 → 60)

### 원인

**구조적 원인은 확인했습니다. 다만 "그 날 실제로 무엇이 실행됐는지"는 확인 못 했습니다.**

`supabase/schema-tl-hotdeal.sql` 125~141행:

```sql
create or replace function public.tl_earned(p_uid uuid) ... as $$
  select
    coalesce((select count(*) from public.trades t where t.user_id = p_uid), 0) * 10
    + greatest(0, coalesce((
        select case when ta.initial_balance > 0
                    then (ta.realized_pnl / ta.initial_balance) * 100 else 0 end
        from public.trading_accounts ta where ta.user_id = p_uid), 0)) * 20
    + coalesce((select pr.rank_points from public.profiles pr where pr.id = p_uid), 0);
$$;
```

**획득 TL 은 저장된 값이 아니라 "지금 남아 있는 거래 기록에서 매번 새로 계산하는 값"입니다.**
세 조각 중 두 조각이 거래에 매달려 있습니다.

| 조각 | 근거 | 초기화하면 |
|---|---|---|
| 청산 거래 건수 × 10 | `public.trades` 행 수 | `delete from trades` → **0** |
| 실현 수익률 × 20 | `trading_accounts.realized_pnl` | `realized_pnl = 0` → **0** |
| 수동 가감점 | `profiles.rank_points` | **남음** |

`reset_season()`(`supabase/schema-reset-season-fix.sql` 50~58행)이 `trades` 를 지우고
`realized_pnl = 0` 으로 되돌립니다.

**72,560 → 60 은 이 구조와 정확히 맞습니다** — 남은 60 이 `profiles.rank_points` 이고,
나머지 72,500 은 전부 거래에서 나온 값이라 거래와 함께 사라진 것입니다.

**추측이라고 명시할 부분:** 그 회원의 `rank_points` 가 실제로 60 인지, 그리고 그 날
실행된 것이 `reset_season()` 인지 다른 초기화 경로인지는 **서버를 봐야 알 수 있어
확인 못 했습니다.** SQL 은 실행하지 않았습니다.

**대표가 실행해서 확인할 것** (읽기만 하는 조회입니다):

```sql
-- 그 회원의 rank_points 가 60 인지, 거래가 정말 0건인지
select p.nickname, p.rank_points, public.tl_earned(p.id) as 획득TL,
       (select count(*) from public.trades t where t.user_id = p.id) as 거래건수,
       ta.realized_pnl, ta.initial_balance
from public.profiles p
left join public.trading_accounts ta on ta.user_id = p.id
where p.nickname = '<닉네임>';
```

### 어디를 어떻게 고칠지

**서버(SQL)만 고치면 됩니다. 사이트 코드는 한 글자도 안 고쳐도 됩니다.**

초기화 직전의 획득 TL 을 `tl_transactions` 에 **양수 한 줄로 박제**해서 이월시킵니다.
`tl_balance()` 는 `획득 + tl_transactions 전체 합계` 이므로(`schema-tl-hotdeal.sql` 145~150행)
거래가 사라져 획득이 0 이 되어도 박제해 둔 줄이 그대로 잔액으로 남습니다.

`reset_season()` 안에서, `delete from public.trades` **보다 앞**에:

```sql
  -- 시즌이 바뀌어도 지금까지 모은 TL 은 그대로 이월합니다.
  -- tl_earned() 는 거래에서 매번 새로 계산하는 값이라, 거래를 지우면
  -- 함께 사라집니다. 지우기 "전"에 그 시점의 값을 한 줄로 박제합니다.
  insert into public.tl_transactions (user_id, amount, kind, memo)
  select p.id, public.tl_earned(p.id), 'grant', '시즌 이월'
  from public.profiles p
  where public.tl_earned(p.id) > 0;
```

(`kind` 에 허용된 값은 `tl_transactions` 정의를 먼저 확인해야 합니다 —
`refund`/`grant` 타입이 이미 정의돼 있다고 `schema-tl-balance-fix.sql` 18행에 적혀 있습니다.)

**그리고 현재 `schema-reset-season-fix.sql` 은 `tl_transactions` 를 비웁니다**
(60~62행 주석: "거래가 사라져 획득 TL 이 0 이 되므로, 사용 기록도 함께 비웁니다").
이월 줄을 넣으려면 **비우는 순서와 함께 다시 설계해야 합니다** —
사용 기록(음수)은 비우고, 이월(양수)은 그 뒤에 넣어야 합니다. 순서가 바뀌면 이월이 날아갑니다.

### ⚠️ 먼저 확인해야 할 것 — 서버에 어느 버전이 올라가 있는지

`docs/인계-보충.md` 207~222행이 경고하는 그대로입니다.
`tl_balance_info` 만 파일 2개, `reset_season` 은 3개입니다.

특히 **`supabase/schema-tl-balance-fix.sql` 이 실행됐는지 여부로 결과가 갈립니다.**

| | 잔액 계산 | 이월(양수) 줄이 |
|---|---|---|
| tl-balance-fix **실행됨** | `balance = tl_balance()` = 획득 + 전체 합계 | **잔액에 반영됨 ✅** |
| tl-balance-fix **미실행** | `balance = 획득 − 음수합계` (양수 무시) | **화면에서 사라짐 ❌** |

미실행 상태에서 이월 줄을 넣으면 **구매 판정은 통과하는데 화면 잔액은 0** 이라는
더 나쁜 상태가 됩니다. **`health-check.sql` 결과부터 확인해야 합니다.**

### 수정 금지 파일 12개를 안 건드리고 되는가

**됩니다.** 서버 함수만 바꿉니다. `js/season.js`·`js/admin.js` 는 열지 않습니다.

### 다른 데가 깨질 위험

- **이미 초기화돼서 TL 이 날아간 회원의 복구는 이 수정으로 안 됩니다.**
  지나간 값은 계산해 낼 근거가 서버에 남아 있지 않을 수 있습니다.
  복구하려면 별도 보정(가상 자산 소급 변경)이라 **누가·얼마에서 얼마로** 를 보고에
  남겨야 합니다 (CLAUDE.md 166~174행)
- 랭킹 점수(`rank_points_all`)도 `tl_earned` 를 쓰므로 순위가 함께 움직일 수 있습니다
- **`tl_earned` 는 손익·랭킹 계산식에 해당합니다 → 대표 확인 대상입니다** (CLAUDE.md 178~184행)

### 되돌리는 방법

```sql
-- ① 이월로 넣은 줄만 지웁니다 (WHERE 있는 DELETE 입니다)
delete from public.tl_transactions where kind = 'grant' and memo = '시즌 이월';
-- ② 함수는 이전 파일을 다시 실행하면 원복됩니다
--    supabase/schema-reset-season-fix.sql 를 그대로 다시 실행
```

지우기 전에 몇 건인지 먼저 셉니다:

```sql
select count(*), sum(amount) from public.tl_transactions
where kind = 'grant' and memo = '시즌 이월';
```

### 확인 방법

**실서버에서 시험하지 않습니다.** 대표가 테스트 계정 하나로:

1. 초기화 전 `tl_balance_info()` 의 `earned` / `balance` 를 적어 둔다
2. `reset_season()` 실행
3. 초기화 후 `balance` 가 **1번과 같은지**, `earned` 는 0 에 가까워졌는지
4. `tl_balance(uid)` 와 `tl_balance_info()->>'balance'` 가 **같은 값인지**
   (`schema-tl-balance-fix.sql` 맨 아래 확인 쿼리가 그대로 있습니다)
5. TL 마켓에서 실제로 구매가 되는지 (잔액이 화면에만 있고 판정에서 막히지 않는지)
